# Session learning and knowledge writeback

Use for every substantive session closeout, including sessions with no repository or source PR. A summary-only request returns text without writes.

## Review how the session worked

Use evidence already present in the conversation: explicit corrections, accepted choices, recurring friction, successful methods, root causes, completed changes and unresolved work. Review the material session, not just the latest assistant answer. Do not rerun product tests or inspect unrelated dashboards.

A durable lesson changes a future decision. Keep one-off task facts in their owning record. Prefer a correction to an existing skill over another skill or a universal checklist. Do not turn an unaccepted suggestion, tentative proposal or one ambiguous example into a permanent user preference.

## Put each delta where it belongs

| Information | Owning location |
|---|---|
| Unfinished work and resume state | Existing project plan or task record |
| Project-specific convention or root cause | Existing project guidance/learnings |
| Reusable workflow correction or accepted working preference | The affected skill and its resources |
| Current company, product or personal knowledge | The selected canonical wiki's owning page |
| Historical evidence or meeting findings | Dated source/summary beside the subject/work |
| Agreed actions | The existing task system during its authorized workflow |

Evaluate skills and wiki relevance on every substantive closeout; update only destinations with a material delta. Wiki/skill updates do not depend on creating or merging a source PR. Keep unmerged work proposed/pending rather than recording it as shipped.

## Apply relevant skill changes

1. Identify the existing skill that owns the behavior, read its current source and affected references/metadata, and reconcile concurrent edits.
2. Capture the smallest supported rule. Keep live prices, client statuses, product facts, private metrics and temporary task mechanics out of general instructions.
3. Use available skill-authoring/maintenance guidance. Reconcile authorized installed counterparts across the user's agents, preserving symlinks, platform adaptations, invocation policy, attribution and private/public boundaries. Update an owned plugin through its source/release workflow, not a disposable cache.
4. Validate changed metadata, references and relevant helper behavior. Publish matching public updates under the user's existing preference; do not export an absent private counterpart.
5. Report installed/local changes separately from a saved plugin release, pushed draft PR or merged public update.

## Apply relevant wiki changes

Use the selected scope's current adapter, live entry instructions and owning pages. Preserve its library or topic-guide layout, file IDs, source dates, access and concurrent changes. Keep one maintained owner per fact and link its evidence; navigation is not another fact register.

Reconcile only supported decisions/corrections, preserve uncertainty and leave unconfirmed owners/dates unset. Private/company/client scopes remain separate. A manual review does not authorize a schedule or new sharing.

Verify canonical readback and required privacy/focused checks, complete the scope's reviewed backup, seal agreement only after both copies match, then refresh only that scope's documented index. Git recovery and generated search results do not supersede the canonical page.

## Finish the authorized scope

An explicit closeout invocation includes the relevant skill/wiki edits under their existing workflows; it is not merely a recommendation pass. Honor summary-only, local-only, no-skills/no-wiki and other narrower instructions. Do not add a new confirmation gate when the session already authorizes the work.

Source-delivery blockers leave independent skill/wiki work actionable. Preserve completed work and report actual access, conflict, validation or publication blockers for the affected portion. State when no durable delta was found rather than manufacturing an update.
