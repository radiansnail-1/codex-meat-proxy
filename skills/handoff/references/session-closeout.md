# Session closeout

Use when the user asks to summarize completed work and update the guidance or knowledge that should carry into future sessions. A plain summary needs only the requested text.

## Capture the material delta

Use the session's existing evidence. Identify completed changes, explicit decisions and corrections, dated measurements, unresolved work and the next action. Distinguish proposed, applied, verified and pending states. Do not rerun product tests, inspect unrelated dashboards or reconstruct the entire conversation.

## Put each lesson where it belongs

| Information | Owning location |
|---|---|
| Unfinished work and resume state | Existing project plan or task record |
| Project-specific operation or convention | Existing project guidance or learnings |
| Current product, company or commercial knowledge | Owning canonical wiki page |
| Reusable workflow correction | The relevant skill and affected resources |

Update only locations affected by a material change. Preserve user-authored TODOs and existing layouts; do not manufacture a new journal or scatter the same fact across every destination. For cloud knowledge, use the canonical source, retain file IDs and follow its backup process. Git recovery copies and generated search indexes do not supersede the canonical page.

Carry explicit corrections forward at their actual scope. A current campaign allowance or product name belongs in its dated owning record, not a generic skill default. A reusable rule for comparing currencies can belong in the campaign skill. Record automation cadence and publishing authority per workflow; manual wiki upkeep and recurring blog publication can coexist. Do not infer a blanket permission or create a schedule.

A request to update skills or project guidance authorizes the relevant edits. Use available skill-authoring/maintenance workflows for substantive skill changes, retaining their local/public boundary and standing publication preferences. Other writes, sharing changes, merges and deployments follow their existing authority; the closeout is not new authorization for them. If the user asked only for recommendations, propose edits rather than applying them.

## Reconcile and verify

Before editing a shared instruction or page, reread the current version. Preserve concurrent changes and revise only the supported delta. Remove directly superseded guidance so future sessions receive one current rule. Check affected metadata, references and links; validate changed skills with their installed validator. These instruction checks are part of the edit, not a product release audit.

Do not force an update when existing guidance already captures the lesson. Report an actual access or integrity blocker while preserving completed work; do not invent a new approval step when the session already authorizes the action.

## Report completion

Give a concise account of the material change, guidance actually updated, relevant validation and any pending publication or next action. Say when no guidance change was needed. Do not claim a local edit is published or a draft PR is merged. A closeout's requested guidance edits do not alone start the canonical checkpoint commit/push workflow.
