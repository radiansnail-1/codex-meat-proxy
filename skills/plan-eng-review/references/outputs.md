# Optional review output examples

Use only the parts that help assess this plan. The entrypoint governs scope, questions, and evidence.

For a meaningful finding, report severity, source location or plan statement, failing scenario, impact, and the smallest useful correction. Keep risks and hypotheses distinct from observed defects.

For an implementation checklist, identify the behavior to change, affected files or components, dependencies, and a concrete verification command or manual flow. Do not invent commands before inspecting the repository.

For complex state or data flow, add a compact Mermaid or ASCII diagram. Update existing relevant diagrams when implementation changes their behavior; do not add diagrams to every file or modify unrelated code during review.

When persistence is requested, prefer a short section in the existing plan: current goal, accepted decisions, open material decisions, next action, and verification. Preserve unfinished owner TODOs. Propose additional TODOs only when valuable; no separate question is required for each item unless the user requests that format.

A concise completion report states the recommendation, material findings, checks performed or planned, and remaining uncertainty. There is no required scoreboard, fixed section count, or ritual follow-up question.
